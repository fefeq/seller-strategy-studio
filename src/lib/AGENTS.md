# src/lib rules

- Theory U: a tab per file in src/components/theory-u/, rules in src/lib/theory-u.ts (tested).
- Self-service funnel: trials table, cohort maths by signup date in src/lib/self-service.ts (tested).
- GTM Advisor: the server fn re-checks the caller's org role and the gtm_advisories RLS limits read/insert to owner and sales_leader; the data snapshot sent to the AI is built by pure code in src/lib/advisor.ts (tested) and the model must answer with its strict JSON schema.
- Onboarding data is defined once in src/lib/setup-schema.ts (items, weights, unlocks, completeness); the AI fill, wizard, interview, sidebar meter and proactive detector all read it, so new required data = one new item there.
- The agent's capabilities live in one registry (src/lib/agent/tools.ts = core tools + the area modules in src/lib/agent/tools/: accounts, pipeline, meetings, inbox; shared types/helpers in tool-kit.ts): read tools run immediately, write tools only create agent_pending_actions executed after explicit confirmation; every handler scopes by org_id explicitly and checks with mustFind/mustBeMember every id it links to (account, deal, segment, member), reads related names with the company filter (accountNames, never an embedded join), because Telegram/cron run it with the privileged client; rules RLS or triggers give the app are enforced in code too (suggestion visibility via canActOnSuggestion, approval deciders, who reassigns a deal, prices/costs/discounts on deal lines only for canPrice roles, personal knowledge docs only for their author). Known gap: the guard_approval trigger reads auth.uid(), so decide_approval fails from Telegram until a migration lets the privileged path pass the decider. A tool reuses the pure function or core the screen uses, never parallel logic: AI generations shared with screens live in src/lib/ai-core.ts (org-scoped when given a scope). A write may return { mensaje } and decidePending appends it to «Hecho: …» (warnings, «enviado a Aprobaciones»). update_deal mirrors Pipeline: a won-kind stage creates a stage_change approval, the MEDDPICC stage gate warns, and a deal with product lines keeps the amount of its lines. Tests with a recording fake client in src/lib/agent-tools.test.ts (expectScoped checks org scoping). After changing tools run `node node_modules/@lovable.dev/mcp-js/dist/cli/extract-manifest.cjs .` to refresh .lovable/mcp/manifest.json, and add the title to TITLES.
- Agent turns run server-side via AI SDK Responses (src/lib/agent/agent.server.ts) and return final text; transcripts store only plain user/assistant text so channels (app, Telegram, future WhatsApp) share one core.
- Proactive rules are pure detectors, one file each in src/lib/proactive/detectors/ (tested in src/lib/proactive.test.ts); suggestions dedupe on (org_id, dedupe_key) so dismissed items never return, and actions reuse agent tools.
- Suggestions: members see own + unassigned, owner/sales_leader see and reassign all (RLS); team panel rules pure in src/lib/suggestion-board.ts (tested); "Para mí" filters own/unassigned explicitly.
- The hourly/daily proactive job is /api/public/jobs/proactive (managed cron auth + job_locks lease); Telegram enters through /api/public/telegram/webhook (secret-token check, idempotent on update_id) and users link via one-time codes in channel_links.
- GTM cycle (BMAD analogy): personas, workflows, phases/next-steps, debate levels and ACV tracks are declarative registries in src/lib/bmad/ (pure, tested in src/lib/bmad.test.ts); artifacts live in gtm_artifacts (versioned, only owner/sales_leader approve, approved ones form the company context every agent loads) and drafting is shared by the server fn and the agent tool via src/lib/bmad/drafting.ts.
- Segment coverage/payback: targets in segment_targets, acquisition costs in cac_costs (channel × segment|shared × quarter), plan vs actual per quarter in segment_budget_quarters (year = sum; old segment_budgets unused). Pure, tested: src/lib/segment-coverage.ts (coverage/payback), src/lib/cac.ts (real CAC, shared split by wins), src/lib/segment-budget.ts (margin: real beats plan, quarter then year, else segment target). Payback = real CAC (else cac_target) with that margin; new payback views pass segments through withPeriodMargin/marginFor.
- Lead intake: external tools post to /api/public/leads with a per-company key (only its SHA-256 lives in lead_sources); CSV goes through importLeads. Both share the pure normalizer in src/lib/leads.ts (tested) and the writer src/lib/leads-ingest.ts (account by domain/name → person by email → lead; a sales stage also writes the deal by external_id/open deal), so every entry path dedupes the same way.
- Leads live in the leads table (Nuevo→Contactado→MQL→SQL→Oportunidad/Descartado); a DB trigger stamps first-reached times per stage and creates the Discovery deal when a lead reaches Oportunidad, so UI, intake, agent and MCP convert identically. Delay limits per company in lead_settings; delay rules and the Lead→Ganado funnel are pure in src/lib/lead-funnel.ts (tested) and shared by the Leads screen, Métricas, agent tools and the late_lead detector.
- Real ACV/win rate/cycle come from src/lib/pipeline-real.ts (pure, tested); useLivePipeline in the app shell listens to realtime deal/lead changes and invalidates every deal-based query key, so new reads of deals must use a key listed there.
- External assistants (Claude, ChatGPT, Codex) connect via the app MCP server at /mcp (src/lib/mcp/, @lovable.dev/mcp-js, Lovable Cloud OAuth): tools are generated from the agent registry and run as the OAuth caller with RLS; MCP writes only create agent_pending_actions (source 'mcp') confirmed in Sugerencias.
- Métricas top panels: QuarterKpisPanel sums the per-segment budget rows into company KPIs per quarter (pure, tested: src/lib/quarter-kpis.ts; payback = customer-weighted segment paybacks; no costs = no CAC, never 0). PipelineBoardPanel (pure, tested: src/lib/pipeline-board.ts) shows open leads (Nuevo→SQL; Oportunidad leads are shown as their deal), opportunities (discovery, qualified), deals in progress (demo→negotiation) and won in the quarter, plus real vs projected CAC/payback (open deals closing in the quarter × real win rate). Both read under the "segment-coverage" key so they refresh live.
- Lead and account score: src/lib/scoring.ts (pure, tested). Fit against the ICP of the account's segment (else the best ICP) over segment, sector, size, anti-ICP and tier; unknown criteria are left out and with none known the fit is null (never 0, and no total). Total = fit 70 % + activity 30 % (recency of touches/meetings/calls/deal updates, open deals; for leads stage progress, recency, delay, scheduled follow-up). Leads inherit their account's fit. Leads, Cuentas, the lead/account detail (ScoreDetail) and the agent's list_leads all call it; new rankings must reuse it instead of ad-hoc ordering.
- Cold deals: src/lib/stale.ts (pure, tested). Threshold = company override (lead_settings.sla.stale_deal_days) else a quarter of the segment's real cycle (pipeline-real.ts) clamped to 14–60 days, else 14. Pipeline, the stale_deal detector (snapshot fields cycleDeals/cycleSegments/staleDays) and the agent's list_deals all call staleDeals(); never hardcode 14 days again. SlaSettings and StaleSettings share the same json, so each saves by merging over the current row.
- Weekly report: src/lib/weekly-report.ts (pure, tested: forward stage moves from deal_stage_history, won/lost, cold via stale.ts, overdue, lead counts, to-do) and weekly-report.server.ts (runs inside the hourly job on Mondays from 06:00 UTC; one suggestion per org and week with detector weekly_report and dedupe key weekly_report:<org>:<monday>; delivered once by Telegram (daily_digest links) and email (src/lib/email.server.ts, Resend, skipped without RESEND_API_KEY) to owner/sales_leader; notified_at marks delivery). syncSuggestions never auto-resolves weekly_report. Owner/Sales Leader can rebuild this week's report from Sugerencias (weekly-report.functions.ts) without sending.
- Follow-up sequence: src/lib/followup.ts (pure, tested). Runs only while a lead sits in Contactado with contacted_at: day 3 (nudge), 7 (value), 14 (breakup), over at 21; a future next_step_at pauses it. The followup_sequence detector emits one suggestion per lead and step (dedupe followup:<lead>:<step>) whose action is update_lead with followupPatch(); late_lead stays quiet while the sequence runs. Template drafts come from positioning/pillars (no AI); the agent's draft_followup (read) asks the AI for an adapted version and never sends.
- Playbook library: src/lib/playbooks/base.ts holds Nokko's five base plays (markers in «» are what the adaptation replaces); src/lib/playbooks/adapt.ts (pure, tested) lists the missing ones by title, builds the prompt and accepts an adaptation only if it kept the numbered structure and no markers. createPlaybookLibrary (playbooks.functions.ts, owner/sales_leader) inserts the missing plays into knowledge_docs (sections playbooks/objections, scope team), adapted with companyContext() when there is setup data, else base text. The meeting brief loads up to 30 knowledge docs (5k chars each) and is told to follow them.
- Call notes: src/lib/call-notes.ts (pure, tested) defines the five lines (meetings.call_notes jsonb: dolor, impacto, decision, freno, siguiente), the call-log entry written to calls (five lines + free notes; the agreed next step wins), the 2 h–7 days reminder (meeting_no_notes detector) and the teardown instructions. The meeting screen, the save_call_notes agent tool and the callTeardown server function (meetings.call_review) all use it; listening coaching reads the five lines too.
- Account assignment: src/lib/assignment.ts (pure, tested) holds countries → regions, rule matching (first by position wins), the deterministic proposal (unowned accounts only, heaviest tier first, lowest tier-weighted load, optional org_members.max_accounts) and the validation of an edited table. Rules live in account_assignment_rules; approval goes only through the apply_account_assignment RPC (role check, maximums, moves open deals/leads, leaves account_assigned suggestions that sync never auto-closes). AI (src/lib/assignment.functions.ts) only proposes rules and phrases the computed reasons; it never assigns. Detector unassigned_accounts needs at least two eligible members.
- Clay (prospecting, stakeholder search, account enrichment) goes only through the connector gateway in src/lib/clay-gateway.ts (server-side, CLAY_API_KEY + LOVABLE_API_KEY read inside the call); filters, mapping to account/stakeholder fields, dedupe by domain/LinkedIn and error texts are pure in src/lib/clay.ts (tested). Screens (clay.functions.ts, any member of the active company) and the read-only agent/MCP tools (agent/tools/clay.ts) call the same three cores; saving results always uses the normal writes (browser client with RLS, or create_account/create_stakeholder/update_account pending actions), never Clay code. Each result spends the Clay workspace allowance, so pages are small (≤25) and continue by search_id.
- Apollo.io goes only through the connector gateway in src/lib/apollo-gateway.ts (same shape as Clay: pure rules in src/lib/apollo.ts, tested; screens via apollo.functions.ts for any member; agent/MCP tools in agent/tools/apollo.ts). Searches and enrichment are read tools; reveals (emails/phones) are write tools because they spend credits and save contact data. Phones are asynchronous: a reveal upserts a pending phone_reveals row (per company, by Apollo person id) and Apollo posts the numbers to /api/public/apollo/phone-webhook (secret in the URL, APOLLO_WEBHOOK_SECRET), which fills every matching row and the stakeholder's phone; a delivered row is reused instead of paying again. The webhook host comes from the request (stable preview host in the editor, published host otherwise; agent/MCP use the published host). Account enrichment reuses Clay's AccountDraft/enrichChanges so both providers propose the same fields.
- Web research uses Firecrawl's direct API (this connection is not gateway-backed: FIRECRAWL_API_KEY with api.firecrawl.dev, src/lib/firecrawl.ts). Pure rules in src/lib/web-research.ts (tested: public URL check, page picking, news cleanup, company name for searches, refresh queue, error texts); cores in src/lib/web-research-core.ts shared by screens (web-research.functions.ts), agent/MCP tools (agent/tools/web.ts) and the hourly job: readCompanySite (onboarding, falls back to the plain fetch), researchAccountCore (plan-of-account proposals, only links that were really read count as sources, saves nothing), refreshSignalsCore (news of the last month classified by AI into account_signals; job refreshes ABM targets weekly, a few per run, stops on no credits; detector account_signal turns actionable ones of the last 7 days into suggestions). researchStakeholderCore (ai-core) searches the web first and cites sources, falling back to hypotheses.
- Perplexity is connected through Lovable's managed gateway, which allows only POST /search (src/lib/perplexity.ts); do not add chat, deep-research or SEC features until a user-owned Perplexity key is connected. Every web search goes through searchBoth (src/lib/web-search.ts): Firecrawl + Perplexity merged and deduplicated, either provider may fail and the other still answers.
- Google Drive is one gateway-backed connection (the builder's Drive, scopes drive.readonly + drive.file) shared by every company, so isolation is in code: src/lib/drive-core.ts gives each company the folder "Nokko / <empresa>" (found by appProperties, row in drive_folders) and every read, listing, search result or linked folder must sit inside it (insideCompany walks parents). drive_folders is written only by drive-core with the admin client after those checks. Writes only land in folders Nokko created (drive.file): saving into a linked folder falls back to the company folder. Pure rules (links, read plan per file type, Markdown→HTML) in src/lib/drive.ts (tested); screens via drive.functions.ts (any member), agent/MCP via agent/tools/drive.ts. Conocimiento «Drive por cuenta» lists every account folder live from Drive; AI summaries are cached in drive_doc_summaries per file and Drive modifiedTime (pure rules in drive-overview.ts, tested) and are only generated on a member's click, never on page load.
- Apify (gateway-backed, APIFY_API_KEY) runs public robots synchronously through src/lib/apify-gateway.ts, each capped by maxItems and maxTotalChargeUsd (the actors and caps live in ACTORS, src/lib/apify.ts, with the pure mapping of posts, jobs and G2 reviews, tested). Cores in src/lib/apify-core.ts: the account's LinkedIn page (accounts.linkedin_url, typed or found by search and saved), company posts + job offers added to refreshSignalsCore (they never block the news), stakeholder posts inside researchStakeholderCore, and G2 reviews → battlecard (saved to knowledge_docs objections only on request). Agent/MCP tools in agent/tools/linkedin.ts.
- PostHog is per company, not the builder's connector (the linked PostHog connector only holds a public phc_ token and is unused): the Owner pastes a personal phx_ key in Conexiones; it is AES-GCM sealed with INTEGRATION_KEYS_SECRET (src/lib/secret-box.server.ts; Vault is not writable from agent migrations) and only column grants let the browser read posthog_connections. src/lib/posthog-sync.server.ts runs HogQL with event names passed as values: active people per company domain → product_usage (replaced each sync, matched to accounts by domain) and sign-up/activation/payment → trials (by posthog_person_id or email; never erases typed dates). Queries, parsing and thresholds are pure in src/lib/product-usage.ts (tested); detectors product_qualified and usage_drop; the hourly job syncs each company every 6 h; agent/MCP tools in agent/tools/product.ts. Nokko itself is not measured with PostHog (user decision).
- Inngest (gateway for sending events: src/lib/inngest/send.server.ts; functions served at /api/public/inngest, verified by the SDK with INNGEST_SIGNING_KEY, built lazily in src/lib/inngest/functions.server.ts; the work itself is plain functions in tasks.server.ts). The hourly cron route pings Inngest and, only while the heartbeat (job_locks «inngest:heartbeat») is under 3 h old, dispatches one org-maintenance run per company (suggestions, Stripe, PostHog, signals, sweep of leads to enrich) instead of the inline loop, so the app keeps working if Inngest is not synced. Lead flow (enrichLead in tasks.server.ts, once per lead: leads.enriched_at; steps recorded in leads.flow, pure rules in src/lib/lead-flow.ts, tested): find or create the account (corporate email domain, else exact name) → completeAccount and findKeyPeople through the orchestrator runner (budget-aware, search only, never reveals contacts) → signals, ICP fit → Jev proposal in the lead_enriched suggestion that sync never auto-closes; «Repetir el flujo» (runLeadFlowNow, force) refreshes it is triggered by intake, the lead screens (leadTouched; runs inline when Inngest is not answering) and the hourly sweep (also in the inline cron mode, 3 leads per company and run). The follow-up sequence also runs as lead-followup with sleeps and cancelOn lead.changed; it creates the same dedupe keys as the followup_sequence detector, so both can coexist. Long tasks run as background_jobs (battlecard, stakeholder research, account signals, Drive PDF import) with a realtime toast; «En segundo plano» buttons show only while Inngest is answering. Which events a lead emits is pure in lead-events.ts (tested).
- Parallel (managed gateway connection, PARALLEL_API_KEY; only search, extract, task runs and responses are allowed) in src/lib/parallel-gateway.ts; pure rules in src/lib/parallel.ts (tested): deep account report = one Task run (processor core, cited fields with confidence from output.basis), ICP list = one Task run (ultra ≤25, ultra2x ≤100, entities {name,url} deduped by domain against accounts), enrichment table = Responses in chunks of 5 (rows matched back by code, name or domain; fills only empty fields, country as ISO, funding/tools appended to notes). Long runs live in research_runs (written only by server code with the admin client after the company check) and are polled with ?timeout=1 by the open screen and, while Inngest answers, by the parallel-run function; a realtime toast announces the result. Parallel Search is also the third source inside searchBoth. Agent/MCP tools in agent/tools/parallel.ts.
- Agent on Gemini: its OpenAI-compatible stream omits tool_calls[].index, which the AI SDK rejects; agent.server.ts pipes Gemini responses through fixGeminiStream (gemini.ts, tested). Keep it on any Gemini streamText call with tools.
- Company logos come only from Logo.dev in the browser (publishable key, src/components/company-logo.tsx + pure logoUrl in src/lib/logos.ts): in colour, dark-theme variant, fallback=404 so a missing logo renders nothing; always beside the written name, never instead of it.
- Lead qualification uses Jev (typesafe/jev-1.13, native /v1/systemone via src/lib/jev.server.ts): the model only returns typed judgments (fit, intent, authority, enough_info, not_buyer, anti_icp, segment) stored raw in leads.qualification; weights, thresholds and the proposed stage are pure code in src/lib/lead-qualification.ts (tested) read with lead_settings.qualification, so changing weights never re-runs AI. qualifyLeadCore (lead-qualify.server.ts) is shared by the screen fn (qualifyLeads, any member, RLS) and enrichLead (proposal goes in the lead_enriched suggestion as an update_lead action); stage moves are always proposed, never automatic, and never backwards.
- AI provider chain: every AI call (ask() in ai-gateway.ts, the chat agent in agent/agent.server.ts incl. Telegram and MCP, lead qualification in jev.server.ts) walks aiProviders() (gemini.ts, tested): own keys first — Lovable Cloud secrets GEMINI_API_KEY, then OPENROUTER_API_KEY (any model via OpenRouter, independent of Lovable) — and the Lovable AI Gateway last. An own-key failure with quota/auth/5xx/network status (shouldFallBack) moves to the next provider (withFallback; the agent only if no write action was proposed yet); Lovable AI Gateway errors are terminal. AI_LOVABLE_FALLBACK=off = own keys only; AI_PROVIDER=lovable = gateway only. Optional: GEMINI_MODEL, GEMINI_AGENT_MODEL, OPENROUTER_MODEL (default openrouter/auto with require_parameters). Never put keys in .env or VITE_ variables.
- Orchestrator: needs → services catalogue, planner and budget rules are pure in src/lib/orchestrator/planner.ts (tested); spend lives in integration_usage, monthly limit in org_budgets (owner writes). New integration features must go through a need, not a per-service button.
- Orchestrator: needs, services and choice rules are pure in src/lib/orchestrator/planner.ts (tested); src/lib/orchestrator/runner.ts executes a need with fallback, logs estimated spend in integration_usage and checks org_budgets (80 % warn, 100 % pauses only automatic work). Screens and agent ask for needs (CompleteAccount/complete_account, KeyPeopleButton/find_key_people, IcpCompaniesButton/find_icp_companies; shared seniority words and paging cursor in orchestrator/search.ts, tested); new integration-backed actions go through the runner, never straight to a gateway.
- Memory: memories table (scope company|user|account, kind, source, learned, pinned, active, supersedes; personal rows only visible to their author via RLS, forgetting = active false). Merge/relevance/prompt rules pure in src/lib/memory.ts (tested); I/O in memory.server.ts (learnFrom = AI extraction with strict schema, never throws; saveFacts dedupes/replaces). The agent prompt loads memoryBlock every turn and learns after each turn; meetings learn after notes are saved (memory.functions.ts); suggestion approve/dismiss is remembered without AI.
- Inicio briefing: src/components/briefing.tsx reads with the browser client (RLS) and words the blocks with pure src/lib/briefing.ts (tested): «Lo que hice solo» (since yesterday 00:00 local: automatic integration_usage, leads through their flow, learned memories, signals, pending suggestions created, finished background jobs), «Necesita tu decisión» (suggestions digest + approvals for leaders + agent actions to confirm), «Hoy» (meetings, tasks due/late, deals past close date, lead follow-ups; own/unassigned unless leader). The daily email must reuse briefing.ts so app and email say the same.
- Descubiertos: discoveries table (unique org+dedupe_key, so dismissed finds never return; rows written only by server code, members decide via decideDiscovery with their RLS client). Pure rules in src/lib/discoveries.ts (tested): keys, AI schemas/parsers for ICP search terms, fit judgments (≥ 60 enters) and competitors, weekly due, dismiss memory. discoverForOrg (discoveries.server.ts) runs weekly per company (job_locks discover:<org>, marked before searching) from Inngest org-maintenance and the inline cron (one company per run), budget-aware via the orchestrator: ICP → AI English search terms → findIcpCompanies → AI fit filter; key people for target accounts with < 2 stakeholders; competitors via searchBoth + AI, minus positioning.competitive_alternative. Accept = account / lead + stakeholder / competitor appended to positioning; dismiss = memory fact. One weekly «discoveries» suggestion that sync never auto-closes.
